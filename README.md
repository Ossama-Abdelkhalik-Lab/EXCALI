# EXCALI

**EX**act **C**auchy-**A**nalytic **L**ambert **I**ntegration. A Fortran Lambert solver using finite thin rectangular contour integrals, with elliptic, parabolic, hyperbolic and multiple-revolution coverage. This repository also preserves the supplied Exact v2.2 serial and vectorized kernels as independent, unchanged baselines.

The extended solver is a **new implementation of Exact v2.2's thin-rectangle ratio**, not a byte-identical version of it. It takes the rectangle's zero-height limit, which needs only real arithmetic, and adds stable conic coordinates and branch safeguards. Compiled-in starter tables (like Exact v2.2's guess table, but in the Lancaster–Blanchard parameter and covering ellipses, hyperbolas and multiple revolutions) put almost every root close enough that one 8-node rectangle is final, with no Newton polish. It does not call the confluent contour solver, ivLam, Izzo or Gooding. On the mixed benchmark on Apple silicon, single solves take 0.88 times ivLam's time per transfer overall (0.73–0.92 per class; 1.02–1.07 for hyperbolas, where velocities are computed in double-double) and the batch entry 0.86–0.99 times Exact v2.2's batches on the cases those solve, with lower error than ivLam at the 99th and 99.9th percentiles in every class; earlier measurements on a Linux x86-64 runner are in the [validation](docs/VALIDATION.md) record. It is portable standard Fortran; CI covers Linux x86-64, Linux ARM64 and macOS; the supplied original's speed claims must not be applied to this extension.

## Build and test

Requires CMake 3.20+ and GNU Fortran. OpenMP is used only to distribute independent original-kernel batch cases; use `-DEXCALI_OPENMP=OFF` for a serial build.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
./build/excali_example
```

An optional profile-guided build makes the solver about 4% faster. It uses the same flags otherwise, including `-fno-fast-math`:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DEXCALI_PGO=GENERATE
cmake --build build -j && ./build/excali_pgo_train
cmake -S . -B build -DEXCALI_PGO=USE && cmake --build build -j
```

`excali` is a standalone library with no external data files or initialization. Its starter tables are compiled in (`src/excali_tables.inc`, regenerated by `python3 tools/gen_tables.py`; NumPy only). `excali_original` is a separate library for the preserved kernels and their adapters. The generated namespaced build copies change only the original module names, to permit both variants in one executable.

## API

```fortran
use excali_solver, only: excali_solve
! Consistent distance/time units; mu uses distance**3/time**2.
call excali_solve(r1, r2, tof, mu, direction, revolutions, branch, v1, v2, status)
! For exactly antipodal endpoints, supply the transfer plane explicitly:
call excali_solve(r1, r2, tof, mu, direction, revolutions, branch, v1, v2, status, plane_normal)
```

- `direction=+1` follows `r1 x r2`; `-1` follows the opposite orientation. It is not a global-z prograde flag.
- `revolutions>=0` counts complete revolutions. `branch=-1/+1` selects the lower/higher universal-anomaly root for multi-revolution transfers. For zero revolutions either value selects the unique root.
- `plane_normal` is perpendicular to both endpoint vectors. Its orientation, multiplied by `direction`, defines the plane for exact antipodal geometry. Coincident and same-ray geometry remain nonunique/unsupported.
- `excali_one` is the normalized (`mu=1`) entry used by the comparison, with the same argument order as `contour_one`; it also returns the geometry-conditioning flag `half`.
- `excali_batch(n, r1, r2, tof, direction, v1, v2, status, half, nrev, branch)` solves `n` normalized cases (arrays `r1(3,n)`, `tof(n)`, ...) with the same results as `excali_one` per case. It runs blocks of 32 cases stage by stage, so independent cases overlap in the processor; under OpenMP, blocks run in parallel.
- Outputs are initialized to NaN on entry. Always check `status` before using them. Finite values alone are not an accuracy certificate.

| Status | Meaning |
|---:|---|
| 0 | Converged solution |
| 1 | Coalesced multi-revolution roots at minimum time |
| 5 | Time below the requested multi-revolution minimum |
| -1 | Invalid inputs |
| -2 | Degenerate geometry or missing/invalid antipodal plane |
| -3 | Nonunique/unsupported collinear geometry with supplied plane |
| -4 | Numerical convergence failure |

`half=-1/0/1` denotes degenerate/ordinary/near-collinear geometry. The dimensional API can solve exactly antipodal cases with a supplied plane; the comparison's C/MEX interface has no plane argument and reports those cases as unsupported.

## Method

A full write-up, from the Negrete–Abdelkhalik paper through Exact v1 and v2.2 to this code, with a flowchart, the code breakdown and the measured results, is in [docs/method/EXCALI_method.pdf](docs/method/EXCALI_method.pdf). Its LaTeX source is alongside (`latexmk -pdf EXCALI_method.tex`).

The original Exact v2.2 uses a lookup-table guess in universal anomaly, an upper-half thin rectangle with eight Gauss–Legendre top nodes and one midpoint on each side, and a Newton correction. It is restricted to zero-revolution elliptic transfers.

The extension keeps the thin rectangle but evaluates its height-to-zero limit. On a real interval `[c-L, c+L]`, with `f = 1/(T-t)` and Gauss–Legendre nodes `x_i` and weights `w_i`,

```
root = c + Q[((x-c) f)'] / Q[f'],    Q[g'] = g(c+L) - g(c-L) - L * sum_i w_i g'(x_i)
```

`Q` is the quadrature error of an exact derivative. The ratio is exact for a simple pole anywhere in the interval, so only the analytic remainder of `1/(T-t)` limits it, as `(L/2R)^(2n)` for the nearest other singularity at distance `R`. It needs `T` at the nodes and endpoints and `T'` at the nodes; `T'` comes from the closed-form ODE derivative. There is no complex arithmetic. Node trigonometry uses angle addition with compile-time constants for power-of-two half-widths, and the half-angle functions of the centre are carried between stages, and into the velocities, by angle addition. Each coordinate has one fused node loop.

**Common path (one rectangle).** The zero-revolution root depends only on the Lancaster–Blanchard parameter `lam` and the time relative to the parabolic time, and the multi-revolution branch roots on `lam`, `1/m` and `sigma = branch*sqrt(1-(t_min/t)^(1/3))`. Compiled-in tables (4×4 cubic interpolation, `tools/gen_tables.py`) give the root, and for multiple revolutions also the minimum time `t_min` and its location `v*`, so feasibility is decided without a search. Near the parabola, outside the tables, a second-order reversion of the series `T(X)` gives the root instead. Each starter is within a few percent of a cheap lower bound on the distance to every singularity of `1/(T-t)`: `min(v, pi-v)` in the elliptic coordinates, `min(w, pi)` or `min(2w, w_b-w)` for hyperbolas, `|X|` near the parabola, `min(xi, 2(wb-xi), pi)` in the distance from the branch point `xi = wb - w` used for very short short-way hyperbolas (where `y = 2b*sinh(wb-xi/2)*sinh(xi/2)` keeps full relative precision), and the distance to `v*` for multiple revolutions. The hyperbolic tables use a grid in `sqrt|tau|`, reaching transfers within about 0.1 degree of 180 degrees. One 8-node rectangle of half-width at most 1/16 of that bound is then final (error about `(1/32)^16`); for zero-revolution ellipses the table is usually close enough for a 3-node rectangle of half-width 1/256 of it (error about `(1/512)^6`). It is accepted only with a sign change of `T - t`, its estimate inside the interval and its error estimate at rounding; in the benchmark this holds for 99.4–100% of the cases the tables cover. Everything else continues on the general path below. Single solves and `excali_batch` run the same code (`excali_one` is one case of the batch stages). Near the parabola and near the short-way hyperbolic branch point, velocities come from Lagrange f,g on the exact inputs in double-double arithmetic (correctly rounded for the computed `y`); elsewhere from the radial/transverse form.

**General path.** Closed-form starter, an 8-node stage with `L ~ R/4`, and, only when the stage's own error estimate is above rounding, a 3-node stage centred on the first estimate. The error estimate is the disagreement of the two independent ratios `Q[((x-c)f)']/Q[f']` and `Q[((x-c)^2 f)']/Q[f']`. `R` is computed analytically: branch points of `sqrt(y)`, the mirror root of the even zero-revolution time function, the other multi-revolution branch, and the complex roots of `T = t` beside a pole of `T` (at `sqrt(3)` times the pole distance). Every accepted interval must show a sign change of `T - t` without containing a pole. An estimate outside its interval re-centres, and an inconsistent one widens the interval. The rare cases whose starter still misses (at most 0.8% by regime) continue as a bracketed contour: the sign of `T - t` at the centre and the rectangle's own sign test shrink the starter's bracket, and every estimate is still a zero-height rectangle ratio. Very short hyperbolas (`t < 0.1 t_p`) outside the tables, or whose rectangle the one-rectangle path rejects, use the same bracketed contour in `sqrt(y)`. The root solve has no Newton step and no complex arithmetic; the only derivative-based iteration is the one- or two-step Halley search for the multi-revolution minimum time. Analytic parabolic limits need no quadrature.

Coordinates are `X = ±x²` near the parabola (a power series, which removes the mirror root), elliptic half anomaly, distance from the upper elliptic pole, hyperbolic half anomaly, and `sqrt(y)` for very short short-way hyperbolas. The last avoids subtracting nearly equal values at the hyperbolic branch point. Long-way hyperbolic time is rearranged algebraically to avoid cancellation. For multiple revolutions, every ellipse through both points has `a >= s/2`, so `T > m*2*pi*(s/2)^1.5` rejects most infeasible times before `T` is evaluated. The table's `t_min` (worst relative error 1.04e-7, including revolution counts between its slices) decides feasibility outside a margin of 1e-6. Within it, or when the table's rectangle is rejected, a Halley search for the minimum time (one or two steps, from the large-`m` minimum of `y^1.5/sin^3 v`) stops as soon as its error bound decides feasibility and places the minimum well inside the distance to the root. Within 1% of the minimum time, the branch starter inverts the local cubic Taylor model. Starters need only a few digits, so they use a bit-pattern cube root with one Halley correction (two for the feasibility test). Branch-point distances use a fast polynomial logarithm, and half-angle sines and cosines a short inline polynomial. Near a pole of `T`, starters solve the pole asymptote `T ~ n*pi*y^1.5/(sqrt2*d^3)` with `y` quadratic in the pole distance `d`, which also covers the plateau of near-full-period long-way transfers. Radial/transverse velocity reconstruction avoids the near-antipodal cancellation of Lagrange coefficients. Logarithmic unit scaling supports very large and very small dimensional inputs.

Geometry, time derivatives, starters and velocity formulas were adapted from `contour_simple`, a short variant of ConfluentContour that has since been removed (it remains in that repository's history); the root iteration was replaced with zero-height rectangle quadrature. EXCALI does not call ConfluentContour.

## Preserved originals

`original/exact_ser.F90`, `exact_vect.F90`, `exact_v1.F90`, `README.txt` and `CHANGES.txt` were copied byte-for-byte from the supplied `Exactv2.2` directory on 2026-10-22. `original/SHA256.json` and the `original_hashes` CTest verify the import. Exact v1 is retained for provenance but is not an active comparison entry. The supplied README contains historical results, not results reproduced by this repository.

Call `exact_initialize()` once, serially, before using `exact_one` or `exact_batch` from `exact_adapter`. The boolean first argument selects the vectorized kernel. These wrappers validate inputs, map direction conventions and reject multi-revolution requests (`-6`). They do not extend the original kernels or repair inaccurate finite answers. Batched arbitrary 3D inputs are rotated into local transfer planes before the original shared-plane API is called, and velocities are rotated back. That work is included in comparison timing.

No license declaration was supplied with these Exact source files; this package does not invent one. No ivLam source, coefficient data, compiled binaries or external submodules are required or bundled.

See [validation](docs/VALIDATION.md) for measured results and limits. The repository is [Ossama-Abdelkhalik-Lab/EXCALI](https://github.com/Ossama-Abdelkhalik-Lab/EXCALI). It can be developed independently or checked out as the `solvers/excali` submodule of Lamberts-Comparison; both use the same Git history.
