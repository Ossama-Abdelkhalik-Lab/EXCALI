# EXCALI

**EX**act **C**auchy-**A**nalytic **L**ambert **I**ntegration. A Fortran Lambert solver using finite thin rectangular contour integrals, with elliptic, parabolic, hyperbolic and multiple-revolution coverage. This repository also preserves the supplied Exact v2.2 serial and vectorized kernels as independent, unchanged baselines.

The extended solver is a **new implementation of Exact v2.2's thin-rectangle ratio**; the original kernels are kept byte for byte in `original/`. It takes the rectangle's zero-height limit, which needs only real arithmetic, and adds stable conic coordinates. Compiled-in starter tables (like Exact v2.2's guess table, but in the Lancaster–Blanchard parameter and covering ellipses, hyperbolas and multiple revolutions) put almost every root close enough that one 8-node rectangle is final, with no Newton polish. Every other case goes to one fixed 32-point formula chosen by region; there is no starter search, retry, bracketing or iteration anywhere. It does not call the confluent contour solver, ivLam, Izzo or Gooding. On the mixed benchmark on Apple silicon, single solves take 0.88 times ivLam's time per transfer overall (0.73–0.92 per class; 1.02–1.07 for hyperbolas, where velocities are computed in double-double) and the batch entry 0.86–0.99 times Exact v2.2's batches on the cases those solve, with lower error than ivLam at the 99th and 99.9th percentiles in every class; earlier measurements on a Linux x86-64 runner are in the [validation](docs/VALIDATION.md) record. It is portable standard Fortran; CI covers Linux x86-64, Linux ARM64 and macOS; the supplied original's speed claims must not be applied to this extension.

## Build and test

Requires CMake 3.20+ and GNU Fortran. OpenMP is used only to distribute independent original-kernel batch cases; use `-DEXCALI_OPENMP=OFF` for a serial build.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
./build/excali_example
```

An optional profile-guided build makes the solver about 4% faster. It uses the same flags otherwise, including `-fno-fast-math`:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DEXCALI_PGO=GENERATE
cmake --build build -j && ./build/excali_pgo_train
cmake -S . -B build -DEXCALI_PGO=USE && cmake --build build -j
```

`excali` is a standalone library with no external data files or initialization. Its starter tables are compiled in (`src/excali_tables.inc`, regenerated by `python3 tools/gen_tables.py`; NumPy only). `excali_original` is a separate library for the preserved kernels and their adapters. The generated namespaced build copies change only the original module names, to permit both variants in one executable.

## API

```fortran
use excali_solver, only: excali_solve
! Consistent distance/time units; mu uses distance**3/time**2.
call excali_solve(r1, r2, tof, mu, direction, revolutions, branch, v1, v2, status)
! For exactly antipodal endpoints, supply the transfer plane explicitly:
call excali_solve(r1, r2, tof, mu, direction, revolutions, branch, v1, v2, status, plane_normal)
```

- `direction=+1` follows `r1 x r2`; `-1` follows the opposite orientation. It is not a global-z prograde flag.
- `revolutions>=0` counts complete revolutions. `branch=-1/+1` selects the lower/higher universal-anomaly root for multi-revolution transfers. For zero revolutions either value selects the unique root.
- `plane_normal` is perpendicular to both endpoint vectors. Its orientation, multiplied by `direction`, defines the plane for exact antipodal geometry. Coincident and same-ray geometry remain nonunique/unsupported.
- `excali_one` is the normalized (`mu=1`) entry used by the comparison, with the same argument order as `contour_one`; it also returns the geometry-conditioning flag `half`.
- `excali_batch(n, r1, r2, tof, direction, v1, v2, status, half, nrev, branch)` solves `n` normalized cases (arrays `r1(3,n)`, `tof(n)`, ...) with the same results as `excali_one` per case. It runs blocks of 32 cases stage by stage, so independent cases overlap in the processor; under OpenMP, blocks run in parallel.
- Outputs are initialized to NaN on entry. Always check `status` before using them. Finite values alone are not an accuracy certificate.

| Status | Meaning |
|---:|---|
| 0 | Converged solution |
| 1 | Coalesced multi-revolution roots at minimum time |
| 5 | Time below the requested multi-revolution minimum |
| -1 | Invalid inputs |
| -2 | Degenerate geometry or missing/invalid antipodal plane |
| -3 | Nonunique/unsupported collinear geometry with supplied plane |
| -4 | Numerical convergence failure |

`half=-1/0/1` denotes degenerate/ordinary/near-collinear geometry. The dimensional API can solve exactly antipodal cases with a supplied plane; the comparison's C/MEX interface has no plane argument and reports those cases as unsupported.

## Method

A full write-up, from the Negrete–Abdelkhalik paper through Exact v1 and v2.2 to this code, with a flowchart, the code breakdown and the measured results, is in [docs/method/EXCALI_method.pdf](docs/method/EXCALI_method.pdf). Its LaTeX source is alongside (`latexmk -pdf EXCALI_method.tex`).

The original Exact v2.2 uses a lookup-table guess in universal anomaly, an upper-half thin rectangle with eight Gauss–Legendre top nodes and one midpoint on each side, and a Newton correction. It is restricted to zero-revolution elliptic transfers.

The extension keeps the thin rectangle but evaluates its height-to-zero limit. On a real interval `[c-L, c+L]`, with `f = 1/(T-t)` and Gauss–Legendre nodes `x_i` and weights `w_i`,

```
root = c + Q[((x-c) f)'] / Q[f'],    Q[g'] = g(c+L) - g(c-L) - L * sum_i w_i g'(x_i)
```

`Q` is the quadrature error of an exact derivative. The ratio is exact for a simple pole anywhere in the interval, so only the analytic remainder of `1/(T-t)` limits it, as `(L/2R)^(2n)` for the nearest other singularity at distance `R`. It needs `T` at the nodes and endpoints and `T'` at the nodes; `T'` comes from the closed-form ODE derivative. There is no complex arithmetic. Node trigonometry uses angle addition with compile-time constants for power-of-two half-widths, and the half-angle functions of the centre are carried between stages, and into the velocities, by angle addition. Each coordinate has one fused node loop.

**Common path (one rectangle).** The zero-revolution root depends only on the Lancaster–Blanchard parameter `lam` and the time relative to the parabolic time, and the multi-revolution branch roots on `lam`, `1/m` and `sigma = branch*sqrt(1-(t_min/t)^(1/3))`. Compiled-in tables (4×4 cubic interpolation, `tools/gen_tables.py`) give the root, and for multiple revolutions also the minimum time `t_min` and its location `v*`, so feasibility is decided without a search. Near the parabola, outside the tables, a second-order reversion of the series `T(X)` gives the root instead. Each starter is within a few percent of a cheap lower bound on the distance to every singularity of `1/(T-t)`: `min(v, pi-v)` in the elliptic coordinates, `min(w, pi)` or `min(2w, w_b-w)` for hyperbolas, `|X|` near the parabola, `min(xi, 2(wb-xi), pi)` in the distance from the branch point `xi = wb - w` used for very short short-way hyperbolas (where `y = 2b*sinh(wb-xi/2)*sinh(xi/2)` keeps full relative precision), and the distance to `v*` for multiple revolutions. The hyperbolic tables use a grid in `sqrt|tau|`, reaching transfers within about 0.1 degree of 180 degrees. Zero-revolution ellipses take a single path: starter, one rectangle, `Q1/Q0`, velocities, with the rectangle's result final. The elliptic table stores the root normalized by its two asymptotes, `(pi-v)/(s*ck)` with `ck = (K/t_p)^(1/3)` from the pole asymptote `T ~ K/(pi-v)^3`, and `v^2*T0'/(t-t_p)` with `T0' = dT/d(v^2)` at the parabola. This absorbs the approach of the `sqrt(y)` branch points to the parabola as `|tau|` grows, and keeps the table within 0.11% of the singularity bound for `|tau| < 0.75` and within 3.9% up to `|tau| = 0.9`. The node count follows from that before the rectangle is evaluated: 3 nodes at half-width bound/256 (error about `(1/512)^6`) for `|tau| < 0.75`, otherwise 8 nodes at bound/8 (error below `1e-19`); the near-parabolic series also uses 8 nodes. Short-way ellipses toward `tau -> 1` (chords down to `1e-12` of the semiperimeter) use a second table, `tabp`, split at `v = pi/2` with `T_half = T(pi/2)`. On the pole side it stores `(pi-v)/(s1*(K/T_half)^(1/3))`, `s1 = (T_half/t)^(1/3)`. On the parabola side it stores `v^2/(s2*(s2+2*e0))`, `s2 = (t-t_p)/(T_half-t_p)`, `e0 = t_p/(T_half-t_p)`, which follows the `sqrt(y)` branch point's boundary layer exactly as `lam -> 1`. It is within 3.1e-5 of the bound for `tau` in `[0.75, 1-1e-6]`, so those ellipses use the 3-node rectangle too. Long-way ellipses at `tau < -0.9` (transfer angles near 360 degrees) go to their region formula below. Hyperbolic and multi-revolution rectangles (8 nodes, half-width at most 1/16 of the bound) are accepted with a sign change of `T - t`, their estimate inside the interval and their error estimate at rounding; the rest continue with the region formulas below. Single solves and `excali_batch` run the same code (`excali_one` is one case of the batch stages). Near the parabola and near the short-way hyperbolic branch point, velocities come from Lagrange f,g on the exact inputs in double-double arithmetic (correctly rounded for the computed `y`); elsewhere from the radial/transverse form.

**Region formulas.** Every case the tables do not settle goes to exactly one fixed formula, chosen by region: the same zero-height ratio with a fixed 24-point Gauss–Legendre rule over a whole region of the root, in a coordinate whose singularities stay away from it. The region and its interval come from the geometry alone, so each case evaluates one formula once. It is accepted with a sign change of `g` at its ends, its estimate inside and its second-moment error estimate small; status -4 reports a failed certificate (none in the validation sets). Zero revolutions, with `f = 1/g`:

| Region | Coordinate | `g` |
|---|---|---|
| ellipse, root `v >= 2`, `b/(y0+b) >= -1/2` | `d = pi - v` on `[-1/2, pi-1.8]` | `sigma - s`, `sigma = (t_p/T)^(1/3)` (linear at the pole) |
| ellipse, root `v >= 2`, `b/(y0+b) < -1/2` | `zeta` with `sin(d/2) = s0 sinh(zeta)`, `s0^2 = y_end/(-2b)`, cut into pieces of length <= 4 | `sigma - s` |
| ellipse, root `v < 2`, `b/(y0+b) > 0.7`; short-way hyperbola with `T(0.9 sqrt(y(pi))) > t` | `Y = sqrt(y)` | `T - t` |
| other ellipses with `v < 2`; hyperbolas with `w <= 1.75` | `X = ±x^2` on `[X_a, 2.2^2]` | `T - t` |
| other hyperbolas | `w` on `[w_e - 2, w_e + 2]`, `w_e = log E`, `t^2 E^2 + c^2 b E - 2c^3 = 0`, `c = y0 + b` | `log(t/T)` |

In `Y` the `sqrt(y)` branch point is regular, so transfer angles near 0 degrees and very short hyperbolas use the same formula as the rest; in `zeta`, `sqrt(y) = sqrt(y_end) cosh(zeta)` is entire and `sigma` is regular at the pole even as `y_end/|b| -> 0` (transfer angles near 360 degrees). The `zeta` interval grows like `log(1/s0)` while its singularities stay at height `pi/2`, so it is cut into equal pieces and the piece with the sign change is used.

For multiple revolutions, every ellipse through both points has `a >= s/2`, so `T > m*2*pi*(s/2)^1.5` rejects most infeasible times before `T` is evaluated. The table's `t_min` (worst relative error 1.04e-7, including revolution counts between its slices) decides feasibility outside a margin of 1e-6. Within it, or when the table's rectangle is rejected, fixed ratios replace any search. The multi-revolution formulas use 32 points. The minimum-time location `v*` is the only zero of `D = T'(v) sin^4 v`, which has no pole and closed-form end values, so one ratio over the whole interval `[0, pi]` gives it. When `|b/(y0+b)| > 0.95` the `sqrt(y)` branch points crowd an end, and the interval becomes `[ve/2, 2ve]` (or its mirror about `pi`) around an asymptotic estimate `ve`, certified by the sign of `D` at its ends. Then `t_min = T(v*)` is exact to rounding and decides feasibility exactly. The branch root uses the same node values in `rho = sign(v-v*) sqrt(1 - (t_min/T)^(1/3))`, which is monotone from -1 to 1 through the fold and both poles; `T - t_min` comes from sum-to-product differences about `v*`. A branch root outside a scaled interval uses `sigma = (t_min/T)^(1/3)` between the pole and that interval, in `zeta` about the pole when the branch points crowd it. Long-way hyperbolic time is rearranged algebraically to avoid cancellation. Radial/transverse velocity reconstruction avoids the near-antipodal cancellation of Lagrange coefficients. Logarithmic unit scaling supports very large and very small dimensional inputs.

Geometry, time derivatives, starters and velocity formulas were adapted from `contour_simple`, a short variant of ConfluentContour that has since been removed (it remains in that repository's history); the root iteration was replaced with zero-height rectangle quadrature. EXCALI does not call ConfluentContour.

## Preserved originals

`original/exact_ser.F90`, `exact_vect.F90`, `exact_v1.F90`, `README.txt` and `CHANGES.txt` were copied byte-for-byte from the supplied `Exactv2.2` directory on 2026-10-22. `original/SHA256.json` and the `original_hashes` CTest verify the import. Exact v1 is retained for provenance but is not an active comparison entry. The supplied README contains historical results, not results reproduced by this repository.

Call `exact_initialize()` once, serially, before using `exact_one` or `exact_batch` from `exact_adapter`. The boolean first argument selects the vectorized kernel. These wrappers validate inputs, map direction conventions and reject multi-revolution requests (`-6`). They do not extend the original kernels or repair inaccurate finite answers. Batched arbitrary 3D inputs are rotated into local transfer planes before the original shared-plane API is called, and velocities are rotated back. That work is included in comparison timing.

The Exact source files came without a license declaration, and this package adds none to them. EXCALI is self-contained: its sources, tables and build files are everything it needs.

See [validation](docs/VALIDATION.md) for measured results and limits. The repository is [Ossama-Abdelkhalik-Lab/EXCALI](https://github.com/Ossama-Abdelkhalik-Lab/EXCALI). It can be developed independently or checked out as the `solvers/excali` submodule of Lamberts-Comparison; both use the same Git history. Commit and push solver changes here first, then record the updated submodule commit in the comparison repository.
