# EXCALI

**EX**act **C**auchy-**A**nalytic **L**ambert **I**ntegration. A Fortran Lambert solver using finite thin rectangular contour integrals, with elliptic, parabolic, hyperbolic and multiple-revolution coverage. This repository also preserves the supplied Exact v2.2 serial and vectorized kernels as independent, unchanged baselines.

The extended solver is a **new implementation of Exact v2.2's thin-rectangle ratio**; the original kernels are kept byte for byte in `original/`. It takes the rectangle's zero-height limit, which needs only real arithmetic, and adds stable conic coordinates. Compiled-in starter tables (like Exact v2.2's guess table, but in the Lancaster–Blanchard parameter and covering ellipses, hyperbolas and multiple revolutions) put almost every root close enough that one rectangle is final, with no Newton polish. Every zero-revolution case, elliptic or hyperbolic, takes one path: a table or closed-form starter, one rectangle, its result final. Multi-revolution cases take one path too: a table starter where the tables reach, and off them (`abs(tau) > 0.9`) two fixed ratios for the minimum time and a closed-form starter, each followed by one rectangle. There is no starter search, retry, bracketing or iteration anywhere. It does not call the confluent contour solver, ivLam, Izzo or Gooding. On the mixed benchmark on Apple silicon, single solves take 0.88 times ivLam's time per transfer overall (0.73–0.92 per class; 1.02–1.07 for hyperbolas, where velocities are computed in double-double) and the batch entry 0.86–0.99 times Exact v2.2's batches on the cases those solve, with lower error than ivLam at the 99th and 99.9th percentiles in every class; earlier measurements on a Linux x86-64 runner are in the [validation](docs/VALIDATION.md) record. It is portable standard Fortran; CI covers Linux x86-64, Linux ARM64 and macOS; the supplied original's speed claims must not be applied to this extension.

## Build and test

Requires CMake 3.20+ and GNU Fortran. OpenMP is used only to distribute independent original-kernel batch cases; use `-DEXCALI_OPENMP=OFF` for a serial build.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
./build/excali_example
```

An optional profile-guided build makes the solver about 4% faster. It uses the same flags otherwise, including `-fno-fast-math`:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DEXCALI_PGO=GENERATE
cmake --build build -j && ./build/excali_pgo_train
cmake -S . -B build -DEXCALI_PGO=USE && cmake --build build -j
```

`excali` is a standalone library with no external data files or initialization. Its starter tables are compiled in (`src/excali_tables.inc`, regenerated by `python3 tools/gen_tables.py`; NumPy only). `excali_original` is a separate library for the preserved kernels and their adapters. The generated namespaced build copies change only the original module names, to permit both variants in one executable.

## API

```fortran
use excali_solver, only: excali_solve
! Consistent distance/time units; mu uses distance**3/time**2.
call excali_solve(r1, r2, tof, mu, direction, revolutions, branch, v1, v2, status)
! For exactly antipodal endpoints, supply the transfer plane explicitly:
call excali_solve(r1, r2, tof, mu, direction, revolutions, branch, v1, v2, status, plane_normal)
```

- `direction=+1` follows `r1 x r2`; `-1` follows the opposite orientation. It is not a global-z prograde flag.
- `revolutions>=0` counts complete revolutions. `branch=-1/+1` selects the lower/higher universal-anomaly root for multi-revolution transfers. For zero revolutions either value selects the unique root.
- `plane_normal` is perpendicular to both endpoint vectors. Its orientation, multiplied by `direction`, defines the plane for exact antipodal geometry. Coincident and same-ray geometry remain nonunique/unsupported.
- `excali_one` is the normalized (`mu=1`) entry used by the comparison, with the same argument order as `contour_one`; it also returns the geometry-conditioning flag `half`.
- `excali_batch(n, r1, r2, tof, direction, v1, v2, status, half, nrev, branch)` solves `n` normalized cases (arrays `r1(3,n)`, `tof(n)`, ...) with the same results as `excali_one` per case. It runs blocks of 32 cases stage by stage, so independent cases overlap in the processor; under OpenMP, blocks run in parallel.
- Outputs are initialized to NaN on entry. Always check `status` before using them. Finite values alone are not an accuracy certificate.

| Status | Meaning |
|---:|---|
| 0 | Converged solution |
| 1 | Coalesced multi-revolution roots at minimum time |
| 2 | Solved, low confidence: the final rectangle's error estimate exceeds 1e-8 of its singularity bound (velocities returned, never re-solved). Seen only within about 3e-9 of a multi-revolution minimum time, where the root is ill-conditioned (accuracy about 1e-8); anywhere else it signals a starter or width regression, and the tests treat it as a failure. |
| 5 | Time below the requested multi-revolution minimum |
| -1 | Invalid inputs |
| -2 | Degenerate geometry or missing/invalid antipodal plane |
| -3 | Nonunique/unsupported collinear geometry with supplied plane |
| -4 | Numerical convergence failure |

`half=-1/0/1` denotes degenerate/ordinary/near-collinear geometry. The dimensional API can solve exactly antipodal cases with a supplied plane; the comparison's C/MEX interface has no plane argument and reports those cases as unsupported.

## Method

A full write-up, from the Negrete–Abdelkhalik paper through Exact v1 and v2.2 to this code, with a flowchart, the code breakdown and the measured results, is in [docs/method/EXCALI_method.pdf](docs/method/EXCALI_method.pdf). Its LaTeX source is alongside (`latexmk -pdf EXCALI_method.tex`).

The original Exact v2.2 uses a lookup-table guess in universal anomaly, an upper-half thin rectangle with eight Gauss–Legendre top nodes and one midpoint on each side, and a Newton correction. It is restricted to zero-revolution elliptic transfers.

The extension keeps the thin rectangle but evaluates its height-to-zero limit. On a real interval `[c-L, c+L]`, with `f = 1/(T-t)` and Gauss–Legendre nodes `x_i` and weights `w_i`,

```
root = c + Q[((x-c) f)'] / Q[f'],    Q[g'] = g(c+L) - g(c-L) - L * sum_i w_i g'(x_i)
```

`Q` is the quadrature error of an exact derivative. The ratio is exact for a simple pole anywhere in the interval. Writing `1/(T-t) = A/(x-r) + h(x)`, `A = 1/T'(r)`, the error is exactly `root - r = Q[((x-r)h)']/Q[f']`: only the Gauss error on the analytic remainder `h` limits it, as `rho^(-2n)` with `rho = |z + sqrt(z^2-1)|`, `z = (x_s - c)/L`, for the nearest other singularity `x_s`, which is `(L/2R)^(2n)` when it lies at distance `R >> L` from the centre. It needs `T` at the nodes and endpoints and `T'` at the nodes; `T'` comes from the closed-form ODE derivative. There is no complex arithmetic. Node trigonometry uses angle addition with compile-time constants for power-of-two half-widths, and the half-angle functions of the centre are carried between stages, and into the velocities, by angle addition. Each coordinate has one fused node loop.

**Common path (one rectangle).** The zero-revolution root depends only on the Lancaster–Blanchard parameter `lam` and the time relative to the parabolic time, and the multi-revolution branch roots on `lam`, `1/m` and `sigma = branch*sqrt(1-(t_min/t)^(1/3))`. Compiled-in tables (single precision, 4×4 cubic interpolation, `tools/gen_tables.py`) give the root, and for multiple revolutions also the minimum time `t_min` and its location `v*`, so feasibility is decided without a search. Near the parabola, outside the tables, a second-order reversion of the series `T(X)` gives the root instead. Each starter is within a few percent of a cheap lower bound on the distance to every singularity of `1/(T-t)`: `min(v, pi-v)` in the elliptic coordinates, `min(w, pi)` or `min(2w, w_b-w)` for hyperbolas, `|X|` near the parabola, `min(xi, 2(wb-xi), pi)` in the distance from the branch point `xi = wb - w` used for the shortest short-way hyperbolas (where `y = 2b*sinh(wb-xi/2)*sinh(xi/2)` keeps full relative precision), and the distance to `v*` for multiple revolutions. Zero-revolution ellipses take a single path: starter, one rectangle, `Q1/Q0`, velocities, with the rectangle's result final. One elliptic table, `tabe` (40 `tau` points by 32), covers every ellipse with `tau` in `[-0.9, 1-1e-6]` (chords down to `1e-12` of the semiperimeter), on a `tau` grid uniform in `sign(tau)(1-sqrt(1-abs(tau)))`, fine toward both ends. It splits at `v = pi/2` with `T_half = T(pi/2)` and stores the root normalized by the asymptote on each side. On the pole side it stores `(pi-v)/(s1*(K/T_half)^(1/3))`, `s1 = (T_half/t)^(1/3)`, with `K` from the pole asymptote `T ~ K/(pi-v)^3`. On the parabola side it stores `v^2/(s2*(s2+2*e0))`, `s2 = (t-t_p)/(T_half-t_p)`, `e0 = t_p/(T_half-t_p)`, which follows the `sqrt(y)` branch point's boundary layer exactly as `lam -> 1`. The starter is within 0.14% of the singularity bound for `tau >= -0.6` (3.2e-5 for `tau >= 0.4`), within 1.5% for `-0.8 <= tau < -0.6` and 5.9% for `-0.9 <= tau < -0.8`. Long-way ellipses at `tau < -0.9` (transfer angles near 360 degrees) use a closed-form starter for `d = pi - v` in `th = t/|b|^1.5` and `eta^2 = 2*y_end/|b|`. In the pole layer it inverts `(pi/4)((1+eta^2/d^2)^1.5-1) = th - pi/4` exactly. Through the transition it uses the cubic `d^3/2 + (th-pi/4) d^2 = 3*pi*eta^2/8`, solved in cancellation-free trigonometric or hyperbolic form. In the body it uses the `tau -> -1` limit, a degree-5 polynomial fit on each half (12 coefficients, within 1.4e-5). The starter is within 6.4% of the bound. Hyperbolas take the same single path. For `u = t/t_p` in `[0.1, 1]` a table on `sqrt|tau|` in `[0, 1]` stores `w^2/((1-u) wn^2)` with `L = 1 - log u`: `wn = L` on the long way, and `wn^2 = L^2 (1 - exp(-wb^2/L^2))` on the short way, so that `wn -> wb` as `tau -> 1` and `wn -> L` as `tau -> 0`, where `wb ~ log(1/tau)` and the two ways meet. Its corrections vanish faster than any power of `tau`; a rational blend leaves a `1/log(tau)` term that costs 20 times the accuracy. The table is within 6.3e-4 of the bound. Faster hyperbolas, `u < 0.1`, use a closed form instead: at large `w`, `T = sqrt2 c sqrt(y)/E` with `E = e^w`, `c = y0 + b`, `y = c - bE/2`, a quadratic in `E`. That gives `w = log E` (long way, or short way with `y >= y0/2`), and for the short way near the branch point `xi` from `y = (tE/(sqrt2 c))^2` exactly, via `cosh w = (c - y)/b` in cancellation-free form. It is within 1.1% of the bound for every `tau`, including the corner of transfers near 180 degrees at the shortest times. Every zero-revolution case therefore takes the same path: starter, one rectangle, `Q1/Q0`, velocities. Multiple revolutions take a single path too wherever the tables reach (`abs(tau) <= 0.9`). The table stores each branch root normalized by its two anchors, `q = (v - v*)/(sigma (P - v*))` with `P` the pole on the branch's side, on one half-grid per branch (16 `tau` points clustered toward `abs(tau) = 0.9` × 12 points uniform in `sqrt(abs(sigma))`). `q` is smooth through the fold and makes `v` hit the pole exactly at `sigma = ±1`, whatever the error of the interpolated `v*`. The starter is within 1.4% of its distance to `v*` (or to the pole) for `abs(sigma) >= 1e-2`; the old table of `v` itself was off by up to 8 times that distance near the fold. One 8-node rectangle at bound/8 is then final (bound/8 rather than /4: the other branch's root can be as close as twice the bound, and the rounding noise of `t_min` is largest there). Near the fold (`abs(sigma) < 1e-2`, or `t` within the table's `t_min` margin) the tabulated `v*` error would dominate, so `mrev_fold` first finds `v*` with one 8-node ratio of `D = T' sin^4 v` about the table's value. That makes `t_min = T(v*)` exact to rounding and decides feasibility exactly. The branch root then starts from the fold series `v = v* + k s (1 - T''' k s/(6 T''))`, `k = sqrt(6 t_min/T'')`, within 0.6% of `abs(v - v*)`, and one rectangle finishes it. No rectangle carries a certificate. Single solves and `excali_batch` run the same code (`excali_one` is one case of the batch stages). Near the parabola and near the short-way hyperbolic branch point, velocities come from Lagrange f,g on the exact inputs in double-double arithmetic (correctly rounded for the computed `y`); elsewhere from the radial/transverse form.

**Zero-revolution regions.** One routine, `zero_rev_start`, picks the region, the coordinate and the starter, and with it the rectangle (`fast_coordinate`), before anything is evaluated:

| Region | Coordinate | Starter |
|---|---|---|
| within 3.1% of the parabolic time | `X = ±x^2` (`x` if `x >= 0.3`) | second-order series reversion |
| ellipse, `tau >= -0.9` | `v` or `pi - v` | `tabe` (clamped beyond `1 - 1e-6`) |
| ellipse, `tau < -0.9` | `v` or `pi - v` | `long_d` closed form |
| hyperbola, `t/t_p >= 0.1` | `w` | `tabh` |
| hyperbola, `t/t_p < 0.1` | `w`, or `xi` near the branch point | large-`w` closed form |

Every starter is within 6.4% of the bound, so every rectangle is the same: 8 nodes at half-width bound/4 (rounded down to a power of two), error about `(1/8)^16`. Its `Q1/Q0` is final. Very close to the parabola (second-order term below `1e-8`) the series itself is the root.

**Off the tables (`abs(tau) > 0.9`).** Multi-revolution cases off the tables take the same three steps in `mrev_edge`, in the coordinate `zeta` about the crowded pole, `sin(x/2) = s0 sinh(zeta)` with `x = v` (short way) or `pi - v` (long way). There `y = y_c cosh^2(zeta)` exactly and `T = A coth^3(zeta)/cos^3(x/2) + sqrt(y_c) cosh(zeta) (±y_c cosh^2(zeta) G(x) + a)`, `A = n pi |b|^1.5/4` (`n = m` short way, `m + 1` long way), `G` the zero-revolution `F`. Every term is evaluated directly, with its `zeta`-derivatives from third-order Taylor arithmetic, so `T` keeps full precision however close the minimum is to the pole (`v*` below `1e-15`).
1. `v*` is the zero of `T'`: an 8-node ratio of `1/T'` over half-width 2 about the large-`m` estimate (in `zeta`, or in `x` when the estimate exceeds 0.2) puts it within 4e-5 of its bound, and a second at bound/16 makes it exact to rounding. `t_min = T(v*)` decides feasibility, matching 50-digit minima to 4e-15.
2. The starter depends on the fold distance `Delta = (t - t_min)/|t_min - A|`: the fold series in `zeta` near the minimum; on the crowded side the pole layer `A coth^3` (closed-form cubics, or `zeta = atanh((A/t)^(1/3))` fitted at `v*`); on the far side the body limit `4 theta cos^3(x/2) = n pi ± (x + sin x)`, `theta = T/|b|^1.5`, inverted from three small tables (`bt_a`, `bt_b`: 8 `1/M` points by 16, normalized so the root keeps its relative accuracy at the body's own minimum and at the pole, within 3e-4), with a fold cubic or a four-term fold model in between, whose quartic is solved by Ferrari's formula. No starter iterates. Every starter is within 15% of the bound.
3. One 8-node rectangle at bound/4 (`min(zeta, |zeta - zeta*|, pi/2, zeta_max - zeta)` in `zeta`, used when `x < 1`; `min(|x - x*|, pi - x)` in `x`, or in `pi - x` above `3pi/4`) is final.

For multiple revolutions, every ellipse through both points has `a >= s/2`, so `T > m*2*pi*(s/2)^1.5` rejects most infeasible times before `T` is evaluated. The table's `t_min` (worst relative error 1.04e-7, including revolution counts between its slices) decides feasibility outside a margin of 1e-6, and `mrev_fold` within it. Off the tables, `mrev_edge`'s exact `t_min` decides it. Long-way hyperbolic time is rearranged algebraically to avoid cancellation. Radial/transverse velocity reconstruction avoids the near-antipodal cancellation of Lagrange coefficients. Logarithmic unit scaling supports very large and very small dimensional inputs.

Geometry, time derivatives, starters and velocity formulas were adapted from `contour_simple`, a short variant of ConfluentContour that has since been removed (it remains in that repository's history); the root iteration was replaced with zero-height rectangle quadrature. EXCALI does not call ConfluentContour.

## Preserved originals

`original/exact_ser.F90`, `exact_vect.F90`, `exact_v1.F90`, `README.txt` and `CHANGES.txt` were copied byte-for-byte from the supplied `Exactv2.2` directory on 2026-10-22. `original/SHA256.json` and the `original_hashes` CTest verify the import. Exact v1 is retained for provenance but is not an active comparison entry. The supplied README contains historical results, not results reproduced by this repository.

Call `exact_initialize()` once, serially, before using `exact_one` or `exact_batch` from `exact_adapter`. The boolean first argument selects the vectorized kernel. These wrappers validate inputs, map direction conventions and reject multi-revolution requests (`-6`). They do not extend the original kernels or repair inaccurate finite answers. Batched arbitrary 3D inputs are rotated into local transfer planes before the original shared-plane API is called, and velocities are rotated back. That work is included in comparison timing.

The Exact source files came without a license declaration, and this package adds none to them. EXCALI is self-contained: its sources, tables and build files are everything it needs.

See [validation](docs/VALIDATION.md) for measured results and limits. The repository is [Ossama-Abdelkhalik-Lab/EXCALI](https://github.com/Ossama-Abdelkhalik-Lab/EXCALI). It can be developed independently or checked out as the `solvers/excali` submodule of Lamberts-Comparison; both use the same Git history. Commit and push solver changes here first, then record the updated submodule commit in the comparison repository.
